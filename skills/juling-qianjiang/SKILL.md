# 拘灵遣将

三个角色，两条不变量：**主将不装内容**，**证据不压缩**。

| 角色 | 谁 | 职责 | 硬边界 |
|---|---|---|---|
| **主将** | 主会话（你） | 立规格、派发、裁决、交付 | 只装指针，不装内容 |
| **探子** | 子代理 `scout` | 只探不谋 | 只读，禁止提案 |
| **监军** | 子代理 `inspector` | 只看成品，不看理由 | 只读，只报告 |

## 为什么这样排

主将是唯一必须活到最后的角色，所以它必须是上下文最小的角色 —— 这两句是同一个约束。

主将一旦自己揽活，上下文就随工作量增长，于是必然压缩，而压缩是「保留故事、丢掉判据」的不可逆操作。把噪音挡在子代理的上下文里，主将的增长就只跟**轮数**有关，与任务大小无关。

由此推出两条不变量，任何一步都不许破：

1. **主将不装内容。** 子代理回报给主将的只有「指针 + 精简摘要」。全文留在子代理自己的上下文里，主将要细节时按路径现取**那一个片段**。
2. **证据永不压缩。** 压缩只能压缩推理。凡是被引用的证据（文件、命令输出、URL、复现步骤）必须在压缩或轮换之前就在磁盘上。

## 产物目录

一律放在项目根的 `.codex-run/`：

- `.codex-run/state/plan.md` —— 状态文件，轮换的唯一依据
- `.codex-run/reviews/` —— 监军的完整审查记录
- `.codex-run/recon/` —— 需要留档的侦察证据

首次创建时提醒用户把 `.codex-run/` 加进 `.gitignore`，除非任务本身就是要把它提交。

## 步骤

### 第 0 步 · 抗命书（动手指前，必须先写）

在动手或派发之前，先记录这道命令本身有没有缺陷。**「无异议」也要付代价**：

```text
[抗命书] 我按 <什么标准> 检查了这道命令。
发现：<缺陷，或「无缺陷」>
如果是 <什么情形>，我就会反对这道命令。
```

只写「无异议」不算完成。写不出「如果是怎样我就会反对」，说明你根本没检查。

命令本身自相矛盾、目标不可能达成、或做法会毁掉用户没说的东西时，**先说出来再动手** —— 这不是顶嘴，这是职责。

### 第 1 步 · 探路（不得跳过）

派 `scout`。**在任何产出之前。**

```text
派发子代理 scout。
要回答的具体问题：<最多 3 个>
范围：<哪个目录 / 哪个文档 / 哪个 API>
不要做：不要提方案，不要改任何文件。
回报格式：≤10 行，分三块（已确认事实+来源指针 / 未知清单 / 反例候选）。
等齐再继续。
```

拿到回报后，**不许乐观解读**。特别看你原本以为已经确定、但 scout 把它列进「未知」的东西 —— 那是这次探路最大的收获。

### 第 2 步 · 冻结规格

写下「这份活按什么标准算做完」，写进 `.codex-run/state/plan.md`，然后冻结。

规格由**你自己**立，这是你唯一能证明自己在工作、而不只是在听话的方式。之后「完成」的定义只能是「规格每条都有证据」，**不是**「用户看起来没生气」。

### 第 3 步 · 执行

能自己做的自己做，但守第 1 条不变量：产物落盘，主将只留指针。

可以并行开工、互不依赖时，一次派发多个子代理并说明「等齐再汇总」。注意：**有先后关系的角色绝不能塞进同一个并行批次**（例如监军必须在成品之后）。

### 第 4 步 · 监军（交付前，不得跳过）

派 `inspector`，把**成品 + 冻结的规格**给它，**不要给推理过程**。

```text
派发子代理 inspector。
成品：<路径>
规格：<逐条列出冻结的验收标准>
你看不到也不需要看主将的推理，不要索要。
回报：≤3 条反对（每条含 什么会坏 / 什么观察能证实 / 判断错的代价）+ 1 条「我最可能错在哪」。
等齐再继续。
```

### 第 5 步 · 裁决

这是整个流程里唯一需要你判断的地方：

- **反对只能用证据驳回，不能用断言驳回。** 意见对意见永远不收敛，只会磨成糊。
- 驳回时写出**你实际做的验证**和它的结果。写不出验证，就接受这条反对。
- 一轮 = 提出 + 应答 + 判定。**两轮不收敛就停下**，把未解决项显式列给用户，不要靠互相妥协收场。
- 监军零反对是合法的，但你要核对它是否写明了检查标准和「如果是怎样就会反对」。没写就等于没审。

### 第 6 步 · 轮换（防止降智）

**轮次预算是信号，不是故障。** 主将每个任务预算 **8 轮**。超预算的正确含义是**「任务该拆了」**，不是「该压缩了」。

**压缩次数 > 1 是设计失败信号。** 与其压缩到降智，不如主动轮换。

阈值（有 `context-gauge` 时用它服务端上报的准确 token 数，不要用推算值）：

```text
python -I ~/.codex/skills/context-gauge/scripts/context_gauge.py --json
```

- 读 `fill_percent`。**≥60%：准备轮换。≥75%：必须轮换。**
- 也读 `compactions`：已经压过 1 次就该轮换，不要等它压第 2 次。
- **没装 `context-gauge` 时降级**：只看轮次预算（8 轮），可以用 `/status` 或 `/statusline` 看当前上下文占用，并**如实告诉用户降级了**。
- **不要用推算的「能力保留率」当闸门。** 那类曲线标定自更早的模型世代，偏悲观，是趋势参考不是绝对数字。更靠得住的信号是**行为退化**：开始重复已否决过的方案 / 忘记未决项 / 把已确认事实说成未知（或反过来）/ 监军的反对开始被无条件接受。行为退化通常比数字更早出现。

轮换步骤：

1. 写 `.codex-run/state/plan.md`，模板见 `references/state-plan-template.md`。
2. **自检**：一个从没见过这次对话的人，只读这一份文件，能不能接着干？不能就补。这一步是整个协议里最要紧的地方 —— 状态文件不自包含，轮换就等于丢上下文，比压缩更糟。
3. **确认证据已落盘**：状态文件里引用的每个文件、命令输出、URL 都还取得到。
4. 给用户一行可直接粘贴的交接语：

```text
请开新会话，第一句发：
读 .codex-run/state/plan.md，按里面的「下一步」接着干。不要问我历史，状态文件就是全部。
```

5. 新会话冷启动时：**先只读状态文件，不要试图回忆或重建旧上下文。**

### 压缩之后（如果没能及时轮换）

压缩后的自我确认不可信 —— 你会以为自己还记得。所以压缩后：

1. 立刻重读 `.codex-run/state/plan.md` 和规格；
2. **重新派一次 `inspector`**，让它拿着状态文件 + 规格独立复核，而不是自己确认「没丢东西」；
3. 任何状态文件里没记的东西，一律当成已经丢了。

## 禁止扮演子代理

**必须真的派发。** 如果派发失败或不可用，就**如实说**「派发不可用，以下是我自己做的」，然后自己做完。

绝对不要自己写「子代理 A 认为……」「scout 报告说……」这种内容。那不是派发，那是把自己的猜测洗成第二方意见，比不派发更糟 —— 它制造了虚假的独立性，让后面的审查全部失效。

判断标准很简单：**子代理的回报是它自己产生的，还是你写的？** 是你写的，就不是子代理。

## 什么时候不要用本 skill

- 一句话能答完的问题、纯查询、闲聊
- 用户明确要求「别绕圈子，直接给我」
- 紧急的小修小补

这些情况下用本 skill 只是浪费 token 和延迟。用户的明确要求优先于本流程。

## 不要做的事

- 不要向用户索要他能自己给你的东西 —— 先派 scout 去查。
- 不要把子代理的完整输出倒进主将上下文，只留指针。
- 不要用推算的「能力保留率」当轮换闸门，用 `fill_percent` 这类准确值加行为退化信号。
- 不要让主将给自己打分。「做完了」必须由规格 + 证据 + 监军来判定。
- 不要在压缩后才想起来写状态文件。状态文件是每轮结束都写。
- 不要以为「派发了」就等于「管好了」。派发只是把噪音挪走，判断仍然是主将的活。
